How vrtti trusts devices

vrtti keeps your notes on a sync server that it does not trust. The server stores and forwards data, yet it cannot read notes or add a device. Two keys per device, one signed log per space, and a signed list of introductions make this work. This follows the Keybase trust model.

1. Keys on each device

Signing key (Ed25519)

The device signs every space log entry and introduction it writes. Any other device checks the signature with the public half.

Encryption key (X25519, age)

Synced notes encrypt for this key. Only the device with the private half can open them.

The private halves never leave the device. The public halves travel together as six lines, the entry key. Space logs and introductions name each device by its entry key:

vrtti-device
d7f3a1…            device id
phone              name
age1q8x…           encryption key (public)
9b4e02c1…          signing key (public, 64 hex)
1795200000000      added at (Unix ms)

2. Each space is a signed chain of entries

A space (for example personal) has its own log. Each entry adds or removes one device, or changes the space color. A current member signs the entry, and the entry holds the SHA-256 hash of the entry before it.

#1 · prev nonecreate phonesigned: phone
hash
→
#2 · prev #1add desktopsigned: phone
hash
→
#3 · prev #2add laptopsigned: desktop
hash
→
#4 · prev #3remove laptopsigned: phone

Each device checks the log from entry 1 (the replay):

  • Entry 1 is a create for this space name by the creator that this device pinned.
  • Each later entry names the same space, holds the hash of the entry before it, and carries the signature of a current member.
  • The check stops at the first entry that fails. Nothing after it counts.

The replay gives the member list. In the example above, the active members are phone and desktop.

Notes of a space encrypt only for its current members and your recovery key. A device outside the personal log holds no key that opens a personal note.

3. Devices meet through signed introductions

A device sees the members of its own spaces. To add a device that shares no space with it yet, the server holds an add-only list of introductions. Each entry says "device B vouches for device D", with B's signature.

Each device works out its known devices:

  1. Itself, and every device that its space logs ever named.
  2. The device that answered its join (vouched for after the reply MAC check).
  3. Every device that a known device vouched for. This repeats until the set stops growing.

Every known device shows in Settings › Devices, where a member can tick it into a space. When another device ticks this one into a new space, this device has no pinned creator yet. It adopts the space only when a known device signed its add entry. The prev hashes then lock the whole chain back to the creator of entry 1.

When you flip the passphrase switch on a device, the device makes a new key pair. Its old key signs a replaces introduction for the new key, so every grid hides the old key once it leaves its spaces.

An introduction gives no space. Only a space log decides who reads a space.

4. A new device joins with a short code

  1. Desktop shows a 10-character code, valid for ten minutes (wrapped in a one-paste vrtti-invite:… line). The server gets only an scrypt verifier, never the code.
  2. The new device sends its entry key with an HMAC proof keyed by the code. The server cannot forge this proof without the code.
  3. Desktop checks the proof, adds the new device to any ticked spaces (zero spaces is fine), and signs an introduction for it.
  4. Desktop replies with the space creators and its own entry key under an HMAC keyed by the code. The new device checks that MAC, pins any creators, and signs an introduction for Desktop.

6. The same model as Keybase

vrtti follows the Keybase trust model, with one change in what counts as a member. In vrtti, a device takes the place of a Keybase user, so each device can belong to some spaces and stay out of others.

7. What this does not protect against

  • A device that someone takes over can change the spaces it belongs to, and lock your other devices out of those spaces. It cannot read or change other spaces.
  • A taken-over device can vouch for a fake key (unchecked in your grids) or make a space such as 000 and add your phone. Your phone opens 000 as Titles only, and its New notes target never switches spaces on its own.
  • A device you remove from a space keeps the notes it downloaded before removal. Removal protects new revisions only.
  • A person who controls the server during a join can guess the code offline. Each guess costs one scrypt run, and the code expires after ten minutes.
  • The recovery key is for emergency decryption only. It plays no part in the trust model.
