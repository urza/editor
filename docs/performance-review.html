02 / 10Client Editor · Critical Finding C2 + H2

Big Files: Why a 5 MB Log Freezes Every Keystroke for Nearly One Second

lang.js has nine language modes and no plain-text mode. DEFAULT_LANG is "markdown", so every .txt, .log, .csv, and scratch note runs @lezer/markdown.

Measured Keystroke Latency on Large Files (Lower Is Better) V8 CPU profile traced 93.8% of 428.9 ms dispatch to @lezer/markdown finishLeaf()

Why It Happens

C2 + H2
  • Unbounded Markdown leaf: Consecutive non-blank lines form one 5 MB Paragraph leaf. finishLeaf() parses the entire leaf synchronously on every keystroke.
  • Whole-table decoration (markdown.js:199): fillsOf() walks every row and cell on every edit and scroll, running /\p{Extended_Pictographic}/u per character.
  • Synchronous word count (statusbar.js:109): Selection changes run countWords(sliceDoc) synchronously. Ctrl+A on 5 MB takes 27.7 ms dispatch / 512.7 ms frame.
  • Whole-file sniff and paste check: lang.js:281 runs JSON.parse() and split("\n") on full multi-MB files. editor.js:348 flattens the full pre-paste doc.

Proposed Solutions

Phase 0
  • Add "plain" mode in lang.js: Map .log, .csv, and .tsv to MODES.plain = () => [].
  • Auto-guard large files: Switch to "plain" above 512 KB or when a single paragraph exceeds 64 KB, with a status bar override. Disable line wrap on lines over 20 KB.
  • Cache table widths + visible rows only: Reuse widths when docChanged is false, build fill widgets only in view.visibleRanges, and fast-path ASCII before regex.
  • Slice and debounce: Debounce selection word count above 20k chars. Slice the first 16 KB in sniff(). Scan before.iterLines() with early exit on paste.

C1

Keep existing <li> rows by data-id and render only the ~40 visible rows in long lists and drawers. DOM nodes stay near ~2,200 at 10,000+ notes, and Recent opens in under 16 ms.

Load only lightweight metadata plus the active note body on boot. Drop eager warmPreviews() (desktop hides previews anyway), decrypt only visible phone rows via a 50-entry LRU, and cap editor.js states at 20 tabs.

04 / 10PWA & Service Worker · Critical Finding C4 + H1

Updates and Cold Start: 23.05 MB Precache Breaks Fast 3G Updates

sw.js caches all 174 files in one versioned cache. Editing one CSS line forces every phone to re-download 19.67 MB of unchanged spellcheck binaries, exceeding the 30 s timeout in capabilities.js:147.

23.05 MB Service Worker Precache Composition (174 Files) 85.3% is spellcheck WASM and Czech dictionary

Two Network Bottlenecks

C4 + H1
  • Monolithic SW cache (sw.js:22): Every deploy re-fetches 15.63 MB Harper + 3.65 MB Czech dictionary + 73 vendor/noble files (including unused post-quantum, bls12-381, secp256k1, and LICENSE files).
  • 121-request cold waterfall: Unbundled ES modules chain across 5 to 7 dependency hops. Cold boot takes 540.9 ms on localhost and 15.7 seconds on Fast 3G.

Proposed Solutions

Phase 1 + 2
  • Three-tier SW caches: Keep vrtti-app-<hash> (~2.5 MB) separate from lazy, asset-hashed vrtti-spell-<hash> (19.7 MB) and vrtti-emoji.
  • Prune vendor/noble: Keep only X25519, Ed25519, ChaCha20-Poly1305, HKDF, SHA-256, and scrypt (drops ~50 files and ~600 KB).
  • Flatten cold waterfall: Generate <link rel="modulepreload"> tags in index.html (or bundle vendored CM6 + noble into 2 files while keeping app/js/ zero-build).
05 / 10Off-Thread Compute · Critical Finding C5 + H3

Phone Freezes: Move Spellcheck WASM and Large-File Crypto to Web Workers

Both Harper (15.6 MB WASM) and Hunspell (4.5 MB WASM + dictionary) load and lint on the main UI thread. Pure-JS age encryption also blocks the main thread on every 300 ms autosave.

Phone (4x CPU) Main-Thread Blocking Tasks vs Worker Target Any task over 50 ms feels like a stutter; over 1,000 ms feels frozen

Spellcheck Worker (spellcheck.js)

C5
  • Run Harper and Hunspell inside one dedicated module Worker (following crypto/unlock.worker.js).
  • Send doc version plus changed paragraphs or viewport slices, and drop stale responses on newer edits.
  • Remove the MAX_DOC_CHARS = 100_000 cutoff safely.
  • Cache score() per paragraph in textlang.js:145 and drop text.split("") in adddiacritics.js:205.

Crypto Worker + Header Slice (age.js)

H3
  • Offload age.encrypt / age.decrypt above 32 KB to a persistent Crypto Worker with zero-copy Uint8Array transfers.
  • Slice up to the "---" header footer in countRecipients() (age.js:127), cutting 5 MB scans from 12.7 ms to < 0.1 ms.
  • Wrap identity and signing keys under one scrypt key in keyring v2 (halving ~4 to 5 s phone passphrase unlock).
06 / 10Sync Client & Search · High Findings H4 + H5

Sync Client and Search: Unbatched Pulls, 20k Truncation, and Unyielded Scans

Large vaults expose strict sequential loops in both sync/client.js and ui/search.js. Both paths can be batched and yielded without changing the protocol or architecture.

Sync Client Problems (sync/client.js)

H4
  • 200x transaction storm (line 1098): pullSpace loops await store.applyRemote(change) one item at a time. Syncing 2,000 notes runs 2,000 IDB transactions, 2,000 sidebar rebuilds, and 2,000 warmPreviews() scans.
  • Silent truncation at 20,000 notes (line 90): MAX_PAGES = 100 silently drops notes past 20,000 in allNotes() and space.backup.
  • Concurrency = 1: push(), rewrapStubs(), reencryptStale(), and backup.js:writeFiles() run one call at a time (100 dirty notes on 150 ms RTT = 15+ s).
  • Titles-only waste: Downloads full bodies and throws away 91.4% to 93.4% of bytes in applyStub().

Sync Client Solutions

Phase 1
  • store.applyRemoteBatch(changes): Commit one 200-change page inside a single IDB readwrite transaction and emit one "change" event.
  • Remove the 100-page cap: Loop while body.hasMore is true, guarded by checking that cursor strictly advances.
  • Bounded pool (4 to 6 workers): Run push, rewrap, reencrypt, and backup writes in parallel.
  • Request ?content=0: Pair with server S3 to cut Titles only traffic by over 90%.

Search Problems (ui/search.js)

H5
  • Starves UI on plaintext tabs (line 344): await store.textOf() resolves in a microtask, never yielding to paint or typing.
  • Wasted allocations (line 189): Calls text.split(/\r?\n/) on every note even with zero hits, and builds DOM nodes for hidden ... N more rows up front.
  • Disk walk traps (line 293): Reads files sequentially (concurrency 1) and walks node_modules, target, dist, bin, and obj.

Search Solutions

Phase 2
  • Fast pre-check: Test indexOf or regex .test() before splitting lines; compute line numbers only around match offsets.
  • Yield and batch DOM: Yield every ~12 ms, batch results into a DocumentFragment every ~50 ms, and render hidden matches only on expand.
  • Skip build folders + parallelize: Skip node_modules / target / dist / bin / obj, read with concurrency 8 (or Rust disk_search on desktop).
07 / 10ASP.NET Core .NET 10 + SQLite · Server Findings S1 to S5

Sync Server: Linear Revision Scans, Overflow Reads, and OOM Risk

Vrtti.Server has only an append-only revisions table and no materialized documents head table. Every 60-second GET /api/spaces poll grows slower as edit history accumulates.

GET /api/spaces Latency vs Total Edit History (Release .NET 10 + Real SQLite) EXPLAIN QUERY PLAN confirms correlated MAX(seq) subqueries and SCAN members

Verified Server Bottlenecks

S1 to S5
  • Correlated scans (SpaceLog.cs:86, Revisions.cs): /api/changes scans all spaces rowid > $since with 3 correlated subqueries + temp B-tree sort.
  • Missing index (Db.cs:122): members has PK (space, device_id); Readable() runs full SCAN members on every request.
  • Unbounded JSON OOM + 91% waste: 200 x 2 MB docs = 400 MB single JSON response; no ?content=0 mode for Titles only.
  • Overflow page reads (Revisions.cs:126): LENGTH(content) reads ~100 MB of overflow pages for 203 revs (69.8 ms). Program.cs loads full content on every POST/GET/DELETE.
  • Double DB open + synchronous = FULL: Auth middleware and handler each open SQLite and run PRAGMA busy_timeout.

Proposed Server Schema & API Fixes

Phase 0 + 1
CREATE TABLE documents (
  doc_id TEXT PRIMARY KEY, space TEXT NOT NULL,
  prev_space TEXT, head_seq INTEGER NOT NULL,
  rev INTEGER NOT NULL, deleted INTEGER NOT NULL,
  updated_at INTEGER NOT NULL, size INTEGER NOT NULL
);
CREATE INDEX documents_space_seq
  ON documents(space, head_seq);
CREATE INDEX members_device
  ON members(device_id, space);
  • Add size INTEGER on revisions insert (kills 69.8 ms overflow scans) and CurrentHead() (skips body except on 409 conflict).
  • Add maxBytes = 4 MB cap and ?content=0 to /api/changes.
  • Share one request-scoped SqliteConnection, set synchronous = NORMAL + cache/mmap pragmas, enable response compression, and add retention/compaction.
08 / 10Tauri Rust Shell · Desktop Findings D1 to D6

Desktop Shell: Blocking Async I/O, Triple-IPC Autosave, and Stat Overhead

src-tauri/src/disk.rs runs synchronous fs_err calls directly on Tokio worker threads, stats every directory entry, and runs three IPC calls plus fsync on every 300 ms file autosave.

Measured Desktop Filesystem & IPC Micro-Benchmarks (Linux ext4) Penalties are larger on Windows NTFS, macOS APFS, cloud folders, and SMB shares

Desktop Shell Gaps

D1 to D6
  • Tokio starvation (disk.rs:798-975): Blocking fs_err calls sit inside pub async fn commands without spawn_blocking.
  • Discarded mtime (native.js:229): disk_write returns Written { mtime }, JS drops it, and docs.js:1372 fires a third disk_stat IPC call.
  • No native search or watcher: JS pulls every folder file over 2 IPC calls and polls open files every 30 seconds.
  • Startup and RAM hazards: Disk::load() runs sync canonicalize() before window open (hangs offline SMB); update.rs:75 pins ~80 MB installer bytes in RAM on "Later"; lib.rs:372 spawns an 8 s sleeping OS thread per load; debug.rs:76 grows without bound.

Proposed Desktop Solutions

Phase 0 + 2
  • spawn_blocking + entry.file_type(): Move all disk I/O off Tokio workers; call fs::metadata() only on symlinks.
  • Single-IPC autosave: Pass expectedMtime into disk_write, return and reuse mtime, and throttle sync_all() to Ctrl+S / blur / 5 s.
  • Binary IPC + Rust disk_search + notify: Use tauri::ipc::Response for text reads/writes, search folders natively in Rust, and replace 30 s polling with OS file watches.
  • Clean startup/memory: Lazy root canonicalization, temp-file installer staging, tokio::time::sleep, and a 500-entry log ring buffer.

Phased Roadmap and Target Performance Budgets

Each phase ships independently as focused PRs with clear before/after benchmark numbers.

Phase 0 · Quick Wins

Eliminate Instant Freezes

  1. Plain mode + large-file guard (lang.js, editor.js): 100x faster 5 MB log editing.
  2. Scoped edit events (editor.js, docs.js, sidebar.js): stop per-key doc.toString() and full redraws.
  3. Markdown table cache (markdown.js): visible widgets + cached widths.
  4. Big-file slices: debounce selection words; slice sniff(), countRecipients(), firstLineTitle().
  5. Server quick wins: members_device index, CurrentHead(), stored size, shared conn, WAL pragmas, compression.
  6. Desktop quick wins: spawn_blocking, file_type(), reuse mtime, temp-file update, ring log, async sleep.
Phase 1 · Scale to 5,000+ Notes

Fast Phones & Slow Links

  1. Three-tier SW cache (sw.js, gen_sw.py): separate 2.5 MB app from 19.7 MB lazy spellcheck; prune vendor/noble.
  2. Virtualized keyed sidebar (sidebar.js): keep DOM near ~2,200 nodes at 10,000+ notes.
  3. IDB meta/bodies split (idb.js, docs.js, editor.js): lazy body loads, drop eager warmPreviews(), 20-tab state LRU.
  4. Batched sync + ?content=0 (sync/client.js): 1 IDB tx per page, drop 20k cap, concurrency 4 to 6, cut 91% stub waste.
  5. Server documents table + 4 MB cap (Db.cs, SpaceLog.cs, Revisions.cs): O(1) space stats and OOM protection.
Phase 2 · Deep Architecture

Zero-Freeze Workers & Native I/O

  1. Spellcheck Web Worker (spellcheck.js, hunspell.js): zero load/lint freezes and lift the 100 KB cutoff.
  2. Crypto Worker + keyring v2 (age.js, keyring.js): off-thread encryption >32 KB and single-scrypt unlock.
  3. Yielding search + Rust disk_search + notify: fast folder search and zero 30 s polling.
  4. Binary IPC + lazy roots (disk.rs, lib.rs): raw UTF-8 transfers and non-blocking offline SMB boot.
  5. History compaction + modulepreload: bounded SQLite disk growth and <3 s Fast 3G cold start.
