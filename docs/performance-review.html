02 / 10Client Editor · Safe Now #1 & #9 (C2 + H2)

Big Files: Why a 5 MB Log Freezes Every Keystroke

lang.js has nine language modes and no plain-text mode. DEFAULT_LANG is "markdown", so every .log, .csv, .tsv, and scratch note runs @lezer/markdown.

Measured Keystroke Latency on Large Files (Lower Is Better) V8 CPU profile traced 93.8% of 428.9 ms dispatch to @lezer/markdown finishLeaf()

Why It Happens

C2 + H2
  • Unbounded Markdown leaf: Consecutive non-blank lines form one 5 MB Paragraph leaf. finishLeaf() parses the entire leaf synchronously on every keystroke.
  • Whole-table decoration (markdown.js:199): fillsOf() walks every row on every edit and scroll, running /\p{Extended_Pictographic}/u per character.
  • Synchronous word count (statusbar.js:109): Selection changes run countWords(sliceDoc) synchronously (5 MB Ctrl+A: 27.7 ms dispatch / 512.7 ms frame).
  • Whole-file sniff and paste check: lang.js:281 runs JSON.parse() and split("\n") on multi-MB text; editor.js:348 flattens the full pre-paste doc.

Safe Solutions Now

Safe Now #1 & #9
  • Add "plain" mode in lang.js: Map .log, .csv, and .tsv to MODES.plain = () => [] (keep .txt on Markdown as lang.js intends).
  • Auto-guard large files: Switch to "plain" above a size limit (for example, 512 KB or a 64 KB paragraph) with a status bar notice and a manual override.
  • Cache table widths + visible rows only: Reuse widths across scrolls, decorate only view.visibleRanges, and fast-path ASCII before regex.
  • Slice and debounce: Debounce selection word count above 20k chars, slice 16 KB in sniff(), and stop the paste blank check at the first non-space character.

04 / 10PWA & Service Worker · Safe Now #3 & #13 (C4 + H1)

Updates and Cold Start: 12.1 MB of Spellcheck Wire Traffic Every Deploy

Live checks on urza.github.io/editor (HTTP/2 + gzip) show a full update sends 13.2 MB on the wire (23.05 MB raw). Spellcheck is 12.1 MB (92%), pushing Fast 3G updates to ~66 s against a 30 s timeout.

13.2 MB Live GitHub Pages Wire Update Breakdown (174 Files) Harper WASM gzips to 8.0 MB; index.dic (3.65 MB) ships uncompressed as text/x-c

Safe Solutions Now

Safe Now #3 & #13
  • Separate precached spellcheck tier (C4): Move Harper, Hunspell, and the Czech dictionary into vrtti-spell-<hash>, kept precached at install for offline use. Preserve it in activate and checkForUpdate() failure cleanup so app deploys drop to ~1.1 MB.
  • Module preload tags (H1): Generate <link rel="modulepreload"> in index.html with a tiny script (like gen_sw.py) to flatten the 121-request cold waterfall while keeping zero-build development.

Deferred to Later Discussion

Later
  • Lazy spellcheck download on first enable: Changes offline guarantees for users who open the app offline before enabling spellcheck.
  • Pruning vendor/noble: Touches the vendored crypto package for a small wire gain.
  • Vendor pre-bundling: Changes the zero-build setup.
05 / 10Off-Thread Compute · Safe Now #10 & #14 (C5 + H3)

Phone Freezes: Move Spellcheck to a Worker and Slice Age Header Reads

Harper (15.6 MB WASM) and Hunspell (4.5 MB WASM + dict) load and lint on the UI thread, freezing Phone 4x for over two seconds. Scrypt already runs in unlock.worker.js so unlock does not freeze input.

Phone (4x CPU) Main-Thread Blocking Tasks vs Worker Target Any task over 50 ms feels like a stutter; over 1,000 ms feels frozen

Safe Now: Spellcheck Worker & Header Slice

Safe Now #10 & #14
  • Harper + Hunspell Worker (C5): spellcheck.js:60 already names WorkerLinter. Move Harper and then Hunspell to a same-origin module Worker, cache score() in textlang.js:145, and remove split("") in adddiacritics.js:205.
  • Header-only countRecipients() (H3): Slice up to "---" (or 64 KB) in age.js:127, cutting 5 MB scans from 12.7 ms to < 0.1 ms.

Later Discussion & Memory Guardrail

Security / RAM
  • Do not parallelize scrypt: scrypt(logN=18, r=8) uses 256 MiB per run. Two parallel runs use 512 MiB and can kill mobile browser tabs.
  • Crypto Worker & v2 keyring: Moving age encryption to a worker moves the device key to the worker, and single-scrypt wrapping changes key format. Both require separate design review.
06 / 10Sync Client & Search · Safe Now #2 & #11 (H4 + H5)

Sync Client and Search: 20k Truncation Bug, Unbatched Pulls, and Unyielded Scans

MAX_PAGES = 100 silently drops notes past 20,000 during large backups. Both pullSpace() and scanTabs() also perform unbatched or unyielded work.

Sync Client Problems (sync/client.js)

H4
  • Data-loss cap at 20,000 notes (line 90): MAX_PAGES = 100 silently truncates allNotes() and space.backup with no error.
  • O(N²) unbatched pull storm (line 1098): In B7, pulling 2,000 Open as tabs notes stalled past 90.0 s with only 1,508 / 2,000 applied (3,023 IDB transactions and 3,012 "change" events).
  • Titles-only bandwidth waste: Pulling 2,000 stubs fired 2,013 IDB tx, 2,000 "change" events, and downloaded 13.84 MB of bodies discarded in applyStub() (91.4% to 93.4% waste).

Safe Sync Solutions Now

Safe Now #2
  • Remove the 100-page cap: Loop while body.more is true and throw an error if next fails to advance.
  • Batch per 200-item page: Apply each page inside one IDB readwrite transaction and emit one "change" event.
  • Request ?content=0: Pair with server S3 to cut Titles only traffic by over 90%. (Parallel push/rewrap stays in Later Discussion.)

Search Problems (ui/search.js)

H5
  • Starves UI on plaintext tabs (line 344): await store.textOf() resolves in a microtask and never yields to paint or typing.
  • Wasted allocations (line 189): Calls text.split(/\r?\n/) on non-matching notes and builds hidden ... N more DOM rows up front.

Safe Search Solutions Now

Safe Now #11
  • Pre-check before split: Test indexOf or regex .test() first; skip split(/\r?\n/) on zero-hit notes.
  • Yield and lazy DOM: Yield every ~12 ms, batch results with DocumentFragment, and create hidden rows on expand. (Default folder skip lists stay in Later Discussion.)

Five targeted SQLite and API fixes land safely today with zero protocol breakage. Keep PRAGMA synchronous = FULL so committed sync pushes never roll back on power loss.

08 / 10Tauri Rust Shell · Safe Now #7 (D1 to D6)

Desktop Shell: Blocking Tokio I/O, Triple-IPC Saves, and Stat Overhead

src-tauri/src/disk.rs runs blocking fs_err calls directly on Tokio async threads, stats every directory entry, and takes three IPC round trips per file save. Keep sync_all() on every save for crash safety.

Measured Desktop Filesystem & IPC Benchmarks (Linux ext4 + Real native.js) Penalties are larger on Windows NTFS, macOS APFS, cloud folders, and SMB shares

Safe Desktop Fixes Now

Safe Now #7
  • spawn_blocking (D1): Wrap all disk_* filesystem work in tauri::async_runtime::spawn_blocking (plain non-async Tauri commands run on the main thread).
  • entry.file_type() (D3): Call fs::metadata() in disk_list only for symlinks (6.6x faster on 5,000 files).
  • Single-IPC save (D2): Return and reuse mtime from native.writeText() and check expectedMtime in Rust before rename.
  • Startup & thread hygiene (D6): Canonicalize saved roots off startup, use tokio::time::sleep instead of an 8 s OS thread, and cap vrttiDesktop.log.

Durability & Later Discussion

Keep sync_all
  • Keep handle.sync_all() on every save: SAVE_DELAY (300 ms) is a debounce that runs once when typing pauses. sync_all() costs ~1 ms on ext4 and prevents empty or stale files after a power cut.
  • Later: Binary IPC for disk_read/disk_write (D4), native Rust disk_search + notify file watcher (D5), and disk-staged update verification (D6).
